Export the hardened XML reader `parseCcda` stands on, and a writer for it, for any XML format.

- `parseXml(text, options?)` reads any XML into an `@xmldom/xmldom` `Document` with every refusal of `parseCcda`'s substrate: a DTD or entity declaration anywhere (`XXE_OR_DTD_PRESENT`), so no external entity is fetched and no entity is expanded; custom entity references over the cap (`ENTITY_EXPANSION_LIMIT`); a text over the size cap; elements nested too deep or too many; and text that is not well-formed or holds a character XML 1.0 forbids. Anything before or after the root element but white space (space, tab, carriage return, line feed), comments and processing instructions is refused as `NOT_WELL_FORMED_XML` too: text, a reference, a stray `<`, a CDATA section or a second element, where `parseCcda` reads past some of it, so no content is dropped or kept beside the root without a word. So is a start tag XML 1.0 makes not well-formed (an unquoted value, an attribute with no value, a quote that does not open or close a value, two attributes with no white space between them, one attribute named twice, a `<` in a value); an `&` that starts no reference (`&`, `&;`, `& name;`, `&#;`) in text or a value; `]]>` in text; what Namespaces in XML 1.0 forbids (two attributes of one element with one namespace and local name through two prefixes, which `@xmldom/xmldom` reads as one, a prefix bound to no namespace, a declaration of the prefix `xmlns`, the prefix `xml` bound to another namespace, the xml namespace under another prefix or as the default, the xmlns namespace under any prefix, a colon in a processing instruction's target); and anything else `@xmldom/xmldom` reports while it reads, even as a warning, but for U+FFFD, which XML allows. Before it returns, it checks that the tree holds as many attributes and child nodes on each element as the text does, so nothing the tree's builder drops is lost without a word. One form that is not well-formed is read: an undeclared entity reference (`&name;`) whose name is ASCII letters, digits and `_`, kept as that text, never expanded, and counted toward `maxEntityExpansions`; one with any other character in its name is refused. A refusal `parseCcda` also makes throws the same `CcdaParseError` code `parseCcda` throws for the same text. The limits are options (`options.limits`, the same `CcdaParseLimits` `parseCcda` takes), and `options.onWarning` receives `ENCODING_BOM_STRIPPED`. It raises no `UNKNOWN_NAMESPACE_PREFIX` and does not check the root element. A limit of `NaN` throws a `TypeError`, since it would turn its cap off; `Infinity` lifts a cap, as it does for `parseCcda`.
- `serializeXml(node)` writes a document (with an XML declaration first, unless it carries one) or an element, with a writer of its own that sends every attribute value, namespace and text through one escaping path and declares every namespace itself. In text, attribute values and namespaces it writes a carriage return, NEL, LINE SEPARATOR and PARAGRAPH SEPARATOR as character references, so a parse keeps them. Before it returns, it reads its own output back with the reader `parseXml` uses and compares the two trees (names, namespaces, attributes, text, CDATA sections, comments, processing instructions, in order); a refusal or a difference throws a `TypeError` naming the kind of node. It also refuses, before writing: a DOCTYPE; `<!DOCTYPE` or `<!ENTITY` inside a comment, CDATA section or processing instruction; a carriage return, NEL, LINE SEPARATOR or PARAGRAPH SEPARATOR in one of those; a processing instruction whose data starts with white space; text other than white space, or a CDATA section, directly under the document; an XML declaration that is not a version, an optional encoding and an optional standalone; a prefixed name with no namespace; one prefix bound to two namespaces on one element; an element with the prefix `xmlns`; an attribute in a namespace with no prefix; a namespace declaration Namespaces in XML 1.0 forbids; a character XML 1.0 forbids; a name that is not an XML name; a comment holding `--`; a CDATA section holding `]]>`; a processing instruction holding `?>`; or a document with no root element. No message names anything the tree holds. The writer does not apply the reader's limits, and the read-back costs a parse of the output on every call.
- A new page, "Parse and write any XML safely", documents both.

Nothing about reading or writing C-CDA changes, and no caller needs to change anything. `parseSecureXml` stays exported as it was.
