Correct four stale claims on the npm package page: the published version, the `ObservationValue` arms, and two about how far the parser's checks reach.

The four claims, in full: the status line said the package was published at `0.0.2` when the registry says `0.0.3`; the discriminated `ObservationValue` union was enumerated as five arms when it has six; the `ManufacturedProduct` arm rules were said to apply at three `consumable` call sites when there are four; and the terminology-adapter note named only the planned medication as the exception when the planned immunization is one too.

ASSETS-P8, the consuming half. The four corrections:

- **The status line said the package was published at `0.0.2`.** Re-derived from the registry with `npm view @cosyte/ccda version`: it is **`0.0.3`**. The same stale claim was on three docs pages, at two different wrong values (`docs-content/installation.md` said `0.0.2`, `docs-content/intro.md` and `docs-content/troubleshooting.md` said `0.0.1`). All four now read `0.0.3`. The historical references elsewhere on the page ("until `0.0.3` the act `<code>` was preferred", and the rest) are legitimate and unchanged.
- **The `ManufacturedProduct` arm rules were said to apply at "the three `consumable` call sites".** There are **four**: a performed Medication Activity, a performed Immunization Activity, a Planned Medication Activity, and a Planned Immunization Activity. The fourth arrived with the Planned Immunization Activity in `0.0.3` and this enumeration was not updated with it, so the page told a consumer that `MEDICATION_PRODUCT_ARM_CONFLICT` and the rest could not fire on a scheduled vaccination, when they do. The troubleshooting page already said four.
- **The terminology-adapter note named only the planned medication as the exception** to "the planned-item codes are never handed to your adapter". A planned **immunization**'s `code` is the vaccine from the same `consumable` and is checked at the `vaccine` slot, exactly as its performed twin is. All three places that carry the note (two on the README, one on the troubleshooting page) now say so, which is also what makes the "five variants whose `code` is the planned act" arithmetic hold in place rather than three sections away.
- **The `ObservationValue` union was enumerated one arm short.** The README listed `physicalQuantity` / `coded` / `string` / `range` / `unsupported`. There are **six**: the missing one is `integer`, which is the arm that carries integer lab values and assessment-scale scores (a PHQ-9 or Glasgow Coma total), and a consumer writing an exhaustive `switch` on the documented five would drop them. The README already documented the `integer` arm correctly in three other places, so only the enumeration was wrong. It now names all six and says so.
**On the README artwork, and one reason corrected.** This entry originally announced a per-package brand banner (`https://cosyte.com/social/cosyte-banner-ccda-1200x300.png`) as a fifth item. That banner is superseded **within this same release** by the shared Cosyte lockup, described in the companion changeset, so it never reached a version a consumer can install and announcing it here would tell a reader they had missed one. The artwork is therefore reported once, from that entry, rather than twice from two.

The reason is recorded as corrected rather than reversed quietly, because it was a stated technical judgement and not a preference. The banner was deliberately a plain markdown image and **not** `<img>` or `<picture>`, on the grounds that whether npm's markdown sanitizer preserves a `<picture>` element was **unverified**. It has since been **measured**: `@cosyte/astm` and `@cosyte/hl7` carry the `<picture>` block on their published pages, GitHub honors the `prefers-color-scheme` switch, and npm hoists the inner `<img>` out of the `<picture>` so the light cut renders there. The premise that made the plain image the safer shape no longer holds, which is what licensed the change.

No runtime, API, or packaging change. Documentation only.
